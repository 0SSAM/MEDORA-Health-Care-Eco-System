# MEDORA Security Remediation Decision | قرار معالجة أمن ميدورا

## English

The white-hat review validated that the deployed application already rejects a cross-site API mutation before routing, returns security headers, scopes scheduled callbacks to authenticated cron identities, keeps API responses out of the service-worker cache, and currently has no high-severity production or complete dependency findings from the package audit. The source scan did not identify a likely committed credential or private-key pattern. The visible GitHub alert endpoints were not authorized for this integration, so they are recorded as a residual review item rather than reported as clear.

Two safe code remediations are approved. First, the current production Content Security Policy permits scripts and connections to every HTTPS origin. The observed live document needs only the application itself, the managed analytics host, and the managed editor dispatcher; the policy will therefore use those explicit origins instead of the HTTPS wildcard. Its HTTPS-upgrade directive will remain active only when the request is already secure, so local production verification does not block its own HTTP test assets. Second, the existing in-memory throttling boundary will expose standards-aligned limit, remaining, reset, and retry metadata. This improves client back-off, operator observability, and defensive behavior without changing endpoint contracts, authentication decisions, database state, or authorization rules. An `Origin-Agent-Cluster` header will be added as a browser isolation hardening measure.

The review deliberately does not change OAuth nonce handling, bearer fallback, password lifecycle, tenant assignment logic, database schema, scheduled-job credentials, or user roles in this cycle. Those controls are already covered by focused contracts and would require broader workflow acceptance. Edge WAF and bot-management configuration cannot be changed from this project code; the final report will provide a safe free-tier operational rule set for the domain administrator.

## العربية

أكدت مراجعة القبعة البيضاء أن التطبيق المنشور يرفض طلبات تعديل الواجهة البرمجية العابرة للموقع قبل التوجيه، ويعيد ترويسات أمنية، ويقصر نداءات المهام المجدولة على هويات Cron الموثقة، ولا يحتفظ بردود الواجهة البرمجية في ذاكرة عامل الخدمة، ولا تظهر مراجعة الحزم الحالية ثغرات معروفة عالية الخطورة في حزم الإنتاج أو في التدقيق الكامل. كما لم يكشف فحص المصدر عن نمط مرجح لمفتاح خاص أو اعتماد مضمّن. ولم تسمح صلاحية التكامل الحالية بقراءة نقاط تنبيه GitHub؛ لذا سُجلت هذه النقطة كمراجعة متبقية بدلاً من الادعاء بأنها خالية.

اعتمدت المعالجة تغييرين إضافيين منخفضي المخاطر. أولاً، تسمح سياسة أمن المحتوى الحالية في الإنتاج بالبرامج النصية والاتصالات إلى كل أصل HTTPS. ويحتاج المستند المنشور المرصود فقط إلى التطبيق نفسه ومضيف التحليلات المدار ومُرسل محرر المنصة؛ لذلك ستستخدم السياسة هذه الأصول الصريحة بدلاً من حرف البدل HTTPS. وستظل تعليمة ترقية HTTP إلى HTTPS فعالة فقط عندما يكون الطلب آمناً بالفعل، حتى لا تمنع التحقق المحلي في وضع الإنتاج من تحميل موارده الاختبارية عبر HTTP. ثانياً، ستضيف طبقة التقييد الموجودة في الذاكرة بيانات معيارية عن الحد والمتبقي ووقت إعادة الضبط وإعادة المحاولة. ويحسن ذلك تراجع العملاء بشكل آمن وقابلية المراقبة الدفاعية دون تغيير عقود نقاط النهاية أو قرارات المصادقة أو حالة قاعدة البيانات أو قواعد الصلاحيات. كما ستُضاف ترويسة `Origin-Agent-Cluster` لتعزيز عزل المتصفح.

لا تغيّر هذه الدورة عمداً معالجة nonce الخاصة بـ OAuth أو بديل Bearer أو دورة كلمة المرور أو منطق تعيين المستأجر أو مخطط قاعدة البيانات أو اعتمادات المهام المجدولة أو أدوار المستخدمين. فهذه الضوابط مشمولة بعقود مركزة، وأي تعديل لها يتطلب قبولاً تشغيلياً أوسع. ولا يمكن ضبط جدار حماية الحافة أو إدارة الروبوتات من كود المشروع؛ وسيعرض التقرير النهائي مجموعة قواعد تشغيلية آمنة للمسؤول على الطبقة المجانية للنطاق.
