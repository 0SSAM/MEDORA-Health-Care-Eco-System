# MEDORA — خطة قبول عميق قائمة على الأدوار

**الحالة:** قيد التنفيذ
**النطاق:** MEDORA Health Care Eco System، وضع العرض المعزول وقراءة عقود الخادم والواجهة.
**سياسة الاختبار:** لا إنشاء لمرضى أو وصفات أو بيانات سريرية تجريبية. لا تنفيذ تلقائي من الذكاء الاصطناعي. لا تجاوز لعزل المؤسسة أو الفرع أو الاختصاص.

## 1. حقائق بيئة الاختبار

بيئة العرض الحالية تهيئ ثلاث هويات فقط، وكلها مقيدة بمؤسسة عرض غير إنتاجية واحدة وفرع واحد واختصاص عرض غير تنظيمي واحد:

| الهوية | الدور في التطبيق | الدور التنظيمي | الاستخدام الحي المسموح |
|---|---|---|---|
| MEDORA Showcase Manager | `manager` | `operations_manager` | الإدارة التشغيلية، المشتريات، التقارير، مسارات الموافقة في نطاق العرض |
| MEDORA Showcase Pharmacist | `pharmacist` | `clinical_lead` | الوصول الصيدلي للقراءة، المخزون، POS حيث تسمح السياسة، والمراجع السريرية فقط |
| MEDORA Showcase Cashier | `cashier` | `staff` | POS وبحث الأصناف وعمليات العرض غير السريرية فقط |

تُستخدم اختبارات العقد والتفويض الخادمية لتغطية أدوار لا توجد لها هوية عرض مستقلة حالياً، مثل المالك، المدير التنظيمي، مسؤول المشتريات، مسؤول المالية، وموظف HR/CRM. لا يُنشأ حساب واسع الصلاحيات اصطناعي لتجاوز ذلك القيد.

## 2. معايير القبول العابرة للأدوار

كل سيناريو يخضع للشروط الآتية قبل اعتباره ناجحاً:

1. تهيئة جلسة ونطاق صحيحين؛ وتشمل قبول الاختصاص القانوني `0` إذا كان مرتبطاً بالفرع.
2. تحقّق خادمي من العضوية في المؤسسة والفرع والاختصاص قبل القراءة أو الكتابة أو التصدير.
3. حجب الوحدة أو الإجراء غير المصرح به بخطأ آمن قابل للفهم، لا بإخفاء واجهة فقط.
4. استخدام المصدر الخادمي نفسه للفلاتر والرسوم والتصدير، مع حماية قيم Excel من الحقن الصيغي.
5. قابلية استخدام RTL وLTR، ولوحة المفاتيح، والبحث الذكي العربي/الإنجليزي مع المطابقة الجزئية وتصحيح تخطيط لوحة المفاتيح.
6. توثيق أثر تدقيقي لكل تغيير تشغيلي مسموح، مع عدم إنشاء معاملة مالية أو سريرية حقيقية خارج بيانات العرض المعزولة.

## 3. مصفوفة الاختبار حسب الدور

| الدور المحاكى | التغطية التشغيلية | إجراءات القبول الأساسية | أسلوب الإثبات |
|---|---|---|---|
| الطبيب/الصيدلي | الوصفات المقيدة، المخزون وFEFO، المراجع ICD-10، المساعد الاستشاري | تهيئة نطاق، وصول قراءة للوصفات، بحث مرجعي غير تشخيصي، رفض الإنشاء أو الصرف عند غياب بيانات سريرية معتمدة، حجب الأعمال الإدارية | جلسة صيدلي حية + عقود السياسة السريرية والتفويض |
| الكاشير/المبيعات | POS، البحث بالاسم والباركود، الفواتير المعلقة، المرتجعات، تقفيل الوردية | تحميل مخزون مقيد، بحث عربي/إنجليزي/باركود، إضافة غير هدّامة حيث يتيح العرض، مسارات رفض التقفيل أو المرتجع غير المصرح | جلسة كاشير حية + اختبارات POS والورديات |
| مسؤول المشتريات والمخزون | الموردون، الائتمان، أوامر الشراء، الاستلام، تحديث الدفعات، التنبؤ | CRUD المورد، رفض كود مكرر، إنشاء/انتقال أمر شراء، استلام idempotent، إثبات عزل الفرع والاختصاص | عقد `procurement` + جلسة مدير العرض ضمن صلاحية operations_manager |
| المالية | الأرصدة، التقارير، القوالب، التصدير والجدولة | فلاتر/فرز معتمدة، تطابق الرسم والتصدير، إنشاء قالب في النطاق، رفض جدولة البريد عند غياب التهيئة، عزل بيانات الطرف المقابل | عقود `procurement.reports` و`reports` + واجهة المدير |
| HR وCRM وخدمة العملاء ومركز الاتصال | جهات اتصال، فرص، عقود، ورديات، مراجعات، تذاكر، SLA، حالات الخدمة | CRUD مقيد، انتقالات الحالة المسموحة، رفض الكتابة خارج النطاق، تذاكر ومهام ورضا العملاء، مساعد قرار استشاري فقط | عقود `secondaryModules` + اختبار واجهة الإداري المتاح |
| مدير الفرع/صاحب القرار | لوحة المؤشرات، التحليلات، التأمين، مكافحة الاحتيال، الذكاء الاصطناعي، الامتثال | عرض المؤشرات والتقارير، مراجعة التوصيات دون تنفيذ تلقائي، فتح قضية/اعتماد وفق الدور، حجب الاتصال الخارجي غير المعتمد | جلسة مدير العرض + عقود `aiInsights` و`antiFraud` و`insurance` |
| مالك النظام/مسؤول المؤسسة | التنظيم، النسخ الاحتياطي، السياسات، المصادقة، الموصلات، حوكمة الذكاء الاصطناعي | إدارة صلاحيات مقيدة، مراقبة النسخ، سياسات مراجعة بشرية، حالة موصلات fail-closed، رفض إدخال بيانات اعتماد أو إرسال خارجي غير متاح | عقود التفويض وسياسة النسخ/الحوكمة؛ لا هوية عرض مستقلة حالياً |

## 4. نطاقات لا يجوز تحويلها إلى نجاح تجريبي

| النطاق | الحكم الحالي | سبب الحظر |
|---|---|---|
| إدخال مرضى أو وصفات أو صرف سريري | محجوب بأمان | لا توجد بيانات عرض سريرية أو مفتاح تشفير وسياسة تفويض معتمدة |
| مطالبات تأمين أو إرسال حكومي خارجي | محجوب بأمان | الموصلات معتمدة كـ `blocked` لحين اعتماد رسمي وبيئة sandbox |
| بريد التقارير المجدول | محجوب بأمان عند غياب مزود البريد | لا يُفعّل التسليم قبل ضبط مزود موثق وأسرار صالحة |
| أدوار شراء/مالية/HR مستقلة حية | مغطاة بعقد خادمي وإداري مقيد | لا توجد هويات عرض مستقلة لتلك الأدوار في القائمة المغلقة |

## 5. ترتيب التنفيذ

1. اختبار العقود الحالية والمحاكاة الحية غير الهدّامة للهويات الثلاث المتاحة.
2. اختبار كل مسار إدارة وتشغيل متبقٍ بعقود تفويض وسياق نطاق صريح.
3. إعادة إنتاج كل فشل قابـل للتكرار من السجل وقراءة السجلات قبل الإصلاح.
4. تطبيق أقل تعديل آمن مع اختبار انحدار مخصص لكل عيب مثبت.
5. تنفيذ Vitest وTypeScript والبناء والتحقق المرئي المكتبي والمتحرك، ثم توثيق الأدلة والقيود.

توجد في هذا السجل معاملات POS تجريبية مقيدة لصنف عرض اصطناعي فقط؛ لا توجد بيانات سريرية أو إدخال مرضى أو وصفات أو إرسال خارجي.

## 7. التحقق النهائي قبل الإصدار

اجتاز فحص TypeScript، ومجموعة Vitest الكاملة (215 ملفاً و662 اختباراً ناجحاً، و9 تخطيات بيئية مقصودة)، وبناء الإنتاج بعد إصلاحات الفصل الوظيفي والحارس المالي. بقي تحذير حجم الحزمة المعروف غير مانع ولم تسجل أخطاء تجميع أو عقود مكسورة.

تحققت لقطة كاملة لمساحة العمل باللغة العربية من سطح مكتب بحجم `1280×720` ومن هاتف بحجم `375×812`. بقي اتجاه RTL، بطاقات الإجراءات، مؤشر الاتصال، المساعد الاستشاري، ومسار البداية قابلة للقراءة ضمن العرضين. تستخدم أداة اللقطات جلسة معاينة مستقلة، ولذلك عرضت نطاقاً غير محدد بدلاً من نطاق المدير؛ لا تُعد بديلاً عن أدلة جلسات المدير والصيدلي والكاشير الحية المسجلة أعلاه.

لم تتطلب الجولة إضافة ميزة جديدة: العيوب المثبتة كانت فجوات تفويض وخصوصية، وعولجت بحواجز خادمية مقيدة واختبارات انحدار. تبقى هويات العرض الحية محصورة في المدير والصيدلي والكاشير؛ أما المشتريات والمالية وHR وCRM وخدمة العملاء والمالك فقد تحققت بعقود خادمية مقيدة وفق المصفوفة بسبب عدم وجود هويات عرض مستقلة لها. لا تزال الميزات الخارجية والسريرية المبينة في القسم 4 محجوبة بأمان إلى حين توافر سياسة واعتماد وتهيئة صالحة.
